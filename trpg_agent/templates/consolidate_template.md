## 铁律（违反即为错误）

1. **只写多段一致且明确的内容**。只有一段提到、且带「（转写存疑）」或明显是场外玩梗的内容
   —— **不要写进 characters/relations**，改为放进 `pending`（待确认）。
2. **剧情/闲聊甄别**：场外闲聊、点外卖、玩梗乱说一律不入库；成人类内容一律不写。
3. **角色 ≠ 玩家**：`name` 是角色名，`played_by` 是 PL 标准称呼（用 canon 的称呼表归一），
   两者不可混用；识别不出 PL 就写 `"待确认"`。
   - ✅ 正确：`{"name": "临海", "played_by": "阿蓝"}` —— 临海是剧内角色，阿蓝是真人玩家
   - ❌ 错误：`{"name": "阿蓝", "played_by": "临海"}` —— **颠倒了**，这是最严重的错误
   - KP 代演的 NPC：`played_by` 写 KP 本人的标准称呼（如 `ReGMeIoN` / `pd`）
   - 草稿里没明说谁演谁 → `played_by: "待确认"`，并往 `pending` 记一条
5. **`events.items` 要写"发生了什么"，不是写段号**：
   - ✅ `"检查信封齿轮发现新撬痕，判断车票来源"`
   - ❌ `"第1段"`（这等于没写）
   同理 `relations[].event` 必须写剧情依据（哪个团、什么事），不能只写段号。
6. **`pending` 不允许为空**：只要存在①角色与玩家的对应②同位体判定③转写存疑的人名
   ④拿不准的设定真伪中的任何一项，就必须写进 `pending`。
   **宁可多记待确认，也不要自信地写错** —— 写错的数据会污染整个宇宙档案。
4. **角色卡/设定稿不算已发生事件**：只写剧情里真实发生的事，`events` 每条注明段号。
5. **复用而不是新建**：canon 名单里已有的角色（尤其是 id 以 `cross_` 开头或标注「跨团」的），
   请放进 `character_updates` 追加 `add_groups`/`append_note`/`add_events`，**不要新建重复节点**。
6. **关系端点必须存在于**：本次 `characters` 新建的角色，或 canon 名单里已入库的角色 id。
   端点不确定就不要写这条关系，放进 `pending`。
7. `strength` 只能是 `强` / `中` / `弱`。`event` 必须带剧情依据（哪个团、什么事）。
8. 新角色 id 前缀统一用 **`{{ID_PREFIX}}_`**（例如 `{{ID_PREFIX}}_zhujue`），全小写拼音/英文。
9. **不要编造**：草稿里没有的内容不能脑补；宁缺勿滥。

## 输出

**只输出一个 JSON 对象**，不要 Markdown 代码围栏，不要任何解释文字。

结构契约：

```json
{{CONTRACT}}
```

字段补充说明：
- `confirmed: true` = 多段一致、明确发生，可以入库；
  `confirmed: false` = 存疑，**必须**同时给出 `pending_reason`（它会进待确认清单，不会写盘）。
- `pending` 数组放所有拿不准的条目（人名归属、同位体判定、设定真伪等），
  每条给 `item`（一句话）+ `reason`（为什么拿不准）+ `segment`（段号）。
- **`players` / `pl_profiles` 的 `uid` 是必填且必须来自 canon 名单**：
  转写稿里通常**没有** QQ uid。所以除非 canon 名单里能查到对应 uid，
  **一律留空数组 `[]`**，把 PL 表现写进 `pending`（例：「小满的 PL 画像待补：语速慢、细节派」）。
  **不要**编造 uid，也不要只写 `name`（缺 uid 的条目会被入库程序拒绝）。
- `id_prefix` 只填前缀本体（如 `xh`），**不要带下划线**；角色的 `id` 才是 `xh_xxx`。
