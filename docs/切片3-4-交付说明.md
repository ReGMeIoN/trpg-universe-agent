# 切片 3 & 4 交付说明（canon / extract / review / visualize / export / housekeep）

> 日期：2026-09-13 · 状态：**已实现并自测通过**（端到端 20/20）
> 对应里程碑：v0.1 全部核心环 + M6 可视化 + M7 KB 包 + M8 收尾

## 一、canon：跨段/跨团一致性的命门

`trpg-agent canon build` 固化三份资产（全部机器可读，可审计）：

| 文件 | 内容 | 规模（生产库实测） |
|---|---|---|
| `.trpg/canon/canon_rules.md` | 铁律 1-12（称呼规范/剧情甄别/杰克档案实时更新等） | 从模板生成，可被 workspace 覆盖 |
| `.trpg/canon/naming.json` | PL 称呼归一表 + 音近归一（pd / 菌羊 / 雪人 / 宽 / 往 / ReGMeIoN…） | 12 条 |
| `.trpg/canon/roster.json` | 已入库名单（id/别名/团/是否跨团） | **137 角色 / 9 个跨团** |

每次提炼注入策略 `extract.roster_scope = group_plus_cross`：
**本团相关 + 跨团常驻**给完整信息（id/别名/扮演/团），其余只给名字做去重参考。
示例团注入块 753 字（≈376 tokens）；生产库按团裁剪，不会把 137 个角色全塞进去。

`canon show` 可预览实际注入内容。

## 二、extract：两阶段提炼

```
分段提炼(扇出)  .trpg/extracts/<团>_段N_提炼.md   ← 模板 + canon 注入 + 段原文
汇总            .trpg/extracts/<团>_汇总.md       ← 模型原始输出(留档)
                .trpg/patches/<团>_patch.json    ← 唯一入库契约(JSON Schema 约束)
```

- **模板资产化**：`templates/extract_template.md`（甄别铁律 + 角色≠玩家 + PL 表现 + 跨团线索 + 待确认）
  与 `templates/consolidate_template.md`（汇总铁律 + 契约 + 反例）。
- **结构化输出**：Ollama 走原生 `format` 传 JSON Schema；OpenAI 兼容走 `response_format` 并自动降级。
- **补丁体检 `lint_patch`**：挡住弱模型常见退化——同 id 重复条目（合并）、自环关系（剔除）、
  `character_updates` 指向本次新增 id（提醒）。体检结果写进 `_meta.lint_warnings`。
- 支持 `--segment N` 单段重跑、`--segments-only` / `--consolidate-only`、`--background`。

## 三、review：待确认闭环

```powershell
trpg-agent review --group 星海列车            # 汇总待确认 -> 生成裁决文件
# 编辑 .trpg/review/<团>_待确认.json 的 decisions
trpg-agent review --group 星海列车 --apply    # 写回补丁(accept/reject/set) + 称呼表(merge)
```

裁决动作：`accept`（确认入库）/ `reject`（驳回，留在待确认）/ `set`（改字段）/
`merge`（把变体并入 canon 称呼表，后续自动遵守）。每次裁决落 `_裁决记录.json` 可审计。

## 四、visualize / export / housekeep

- **visualize**：团关系图 HTML（内联 SVG 群像 + 头像 + 点击弹窗详情，**零外部依赖**）、
  PL 画像墙 HTML、`<团>_关系网.md`、`杰克档案.md`、`跑团宇宙总览.md`。
- **export**：KB 包（`00_跑团宇宙总览` / `00b_杰克档案` / `00c_PL档案` + 各团文档）→ `产出/astrbot知识库导入/`。
- **housekeep**：`产出/收尾清单.md`（数据量 / 团分布 / 九步状态 / 待确认 / 已停用来源团）。

### 安全原则（重要）

| 场景 | 行为 |
|---|---|
| 目标文件不存在 / 首行带 `AUTO-GENERATED` 标记 | 直接生成 |
| 目标文件是**人工维护**的（如生产库的 `杰克档案.md`、`跑团宇宙编年史.md`） | **不覆盖**，改写 `<work>/reports/<名>_自动更新建议.md` 并告警 |
| KB 包里非本工具生成的既有文件 | 跳过并列出（要覆盖需 `export.overwrite_unmanaged: true`） |
| `groups` 字段里混入的标签脏值（如「跨团」） | 统一守卫 `data_utils.is_real_group`，不当团处理 |

> 实盘发现：生产库有 **8 个角色**把「跨团」写进了 `groups`（应是 `tags`）。既有脚本按关键词过滤所以没暴露，
> 但会在导出/统计里凭空造出一个叫「跨团」的团。已守卫；**是否修正这批数据（把「跨团」从 groups 移除）需主人确认**。

## 五、验证证据（真实输出）

**端到端测试**（脱敏示例团，`.venv\Scripts\python.exe tests\test_e2e.py`）→ **20/20 通过**：
ingest(2 素材/2 团) → segment(转写线 3 段 + QQ 线 1 段) → store(工作副本 角色4/更新1/关系3/待确认5,
称呼归一 3) → store --apply(5 角色/3 关系/4 备份/复验通过) → visualize(5 节点关系图 + PL墙 + 关系网 md)
→ export(5 份 KB) → housekeep(数据量一致)。

**真实规模**（137 角色 / 128 关系的数据副本，零风险）：

```
11 个团关系图:  救赎线 27 节点/22 边 · 木柜子 24/16 · 恋爱 14/17 · 魔法少女2 14/17
               致无名者 14/12 · 巨鲨 13/6 · 魔女裁判厅 13/10 · 魔法少女五 10/7 …
```

**一键工作流**：`trpg-agent run --ws <示例团>` → `ingest -> segment -> visualize -> export -> housekeep`
（无音频时转写步骤优雅跳过）。

## 六、模型质量的实测结论（重要）

| 模型 | 分段提炼 | 汇总成补丁 | 结论 |
|---|---|---|---|
| qwen2.5:7b（GPU/FA-off，13~15 tok/s） | 结构合规 | **角色/玩家颠倒、丢 PC、自环关系、重复条目、`pending:[]`** | **不足以承担生产提炼** |
| qwen2.5:14b（第一次尝试） | 结构合规 | 4 角色/4 关系，但角色与玩家仍颠倒 | 更好，但需 3.6GB 主机内存 |

**改进模板后**（加入「角色≠玩家」反例 + 要求 `events` 写事件而非段号 + 要求 `pending` 不得为空），
7b 的纪律性明显提升（`待确认 2`、开始用 `character_updates` 复用既有角色），
但**语义判断仍不可靠** —— 这是模型规模问题，不是管线问题。

**建议**：生产提炼用云端模型（`llm.routes.extract: main` + `TRPG_LLM_KEY`）或至少 14b；
7b 只适合跑通流程 / 做冒烟。管线这一侧已经用 `lint_patch` 尽力兜底。

## 七、已知限制（留给 v0.2）

1. **汇总阶段仍是"一次大 prompt 出整个补丁"**：段多了会超上下文；更稳的做法是
   先机械合并各段 JSON（确定性部分），再用 LLM 只做判断类决策。
2. `review` 的裁决文件需要手改 JSON；可做成交互式逐条确认。
3. `编年史` 目前只出建议文件（因为生产库那份是人工精修的），未做结构化生成。
4. `visualize.net_engine: echarts` 仅占位（沿用已验证的 SVG）。
5. `.doc`（OLE 二进制）只归类不提取。
