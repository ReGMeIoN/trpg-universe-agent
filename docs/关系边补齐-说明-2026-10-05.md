# 全库关系边补齐 · 说明

> 2026-10-05 收工后追加。起因：主人看魔法少女6 的关系图时问「**关系线是不是太少了**」。
> 数据一查——**不是错觉，而且这不是那一团的问题**：全库 13 个团里 12 个都有这个毛病。
> 本文件记录诊断 → 补法 → 两团试点 → 其余 11 团批量补齐。
>
> **一句话结果**：生产库关系边 **194 → 442**；孤立角色（图上没有任何连线的人）
> **62 → 10**，剩下 10 个都是**材料里真的没证据**的（小群没转写 / 骰娘机器人 / 转写没点名）。

## 一、诊断：`extract` 抽关系的口径太小

| 团 | 节点 | 团内边 | 边/节点 | **一条边都没有的孤立角色** |
|---|---|---|---|---|
| **魔法少女育成计划 6** | 48 | **23** | 0.48 | **22 / 48** |
| **阴阳差事录 超自然怪谈** | 29 | **8** | 0.28 | **15 / 29** |

对照组：圣剑英雄谭 26 节点 / 28 边（1.08）、恋爱与命运 15/18（1.20）、魔法少女2 14/18（1.29）。

**根因**：`extract` 的主要职责是抽**角色骨架**，关系只是顺带；它落下的边基本只有
「师徒/辅导配对」这类明确写在卡面上的，**考核官↔考生、灵宠归属、对手对局、同队、亲属、
宿敌、被救/救助** 全漏了 —— 于是近乎一半的角色在图上是个孤零零的头像。

这不是新问题：**圣剑英雄谭当年就是这么补的**（`_extract_relations_sjt.py` +
`_merge_relations_sjt.py`，补了 +22 条边，边/节点从 ~0.23 拉到 1.08）。本轮的差别是把那套
**参数化 + 加了一条 events 回退源 + 补上覆盖率检查**，做成了能一次铺全库的东西。

## 二、做法（四步，可重放）

```powershell
cd <仓库>
$env:PYTHONIOENCODING='utf-8'
$env:TRPG_LLM_KEY = [Environment]::GetEnvironmentVariable('TRPG_LLM_KEY','User')   # 云端提炼必需

# 0) 先体检：边/节点 < 0.8 或 孤立角色 > 节点/5 → 基本就是抽漏了
.\.venv\Scripts\python.exe tools\_relation_stats.py [--group "X" --list]

# 1) 从**材料**抽关系 → 只写草稿，不碰生产库
#    材料自动选：有 <团>_剧情编年史.md 就用编年史，否则退化为 characters.json 的事件纪要
.\.venv\Scripts\python.exe tools\_extract_relations.py --group "<团名>" [--source chronicle|events]

# 2) 草稿合并进入库补丁（去重键 = (from,to,type)，与 store 一致；补丁不存在会自动新建）
.\.venv\Scripts\python.exe tools\_merge_relations.py --group "<团名>"          # dry-run
.\.venv\Scripts\python.exe tools\_merge_relations.py --group "<团名>" --write

# 3) 影子库预演（生产库零风险）——实测 characters.json 零差异、relations 只多不少
.\.venv\Scripts\python.exe tools\_shadow_sync.py --apply
.\.venv\Scripts\python.exe -m trpg_agent store --apply --ws "<工作区>\.trpg\shadow_ws" --group "<团名>"

# 4) 回填生产库 + 重出关系图 + 复验
.\.venv\Scripts\python.exe -m trpg_agent store --apply --allow-production --group "<团名>"
.\.venv\Scripts\python.exe -m trpg_agent visualize --group "<团名>"
.\.venv\Scripts\python.exe tools\_relation_stats.py --group "<团名>" --list
.\.venv\Scripts\python.exe tools\check_html.py "<工作区>\产出"
```

### 全库一把梭（推荐）

```powershell
.\.venv\Scripts\python.exe tools\_relation_fill_all.py            # dry-run：列出需要补的团
.\.venv\Scripts\python.exe tools\_relation_fill_all.py --write    # 抽→并→影子预演→入库→重出图
.\.venv\Scripts\python.exe tools\_relation_fill_all.py --group "X" --write
```

它自己挑「孤立角色 > 0」的团（`DONE` 里的团会跳过，免得重复喂 LLM），
对**新建补丁**这条路径会先拿一个团做影子预演，最后打前后对比表。

### 关键的四个设计点

1. **把「当前孤立角色」单独喂给模型、要求逐个核对** —— 这是覆盖率的关键。
   不这么写，模型只围着主角团转、把边缘 NPC 继续晾着。全库实测覆盖 **62→10**。
2. **目标条数按角色数自适应**（约 0.9~1.4 边/人），不要写死「20~40 条」——
   48 人的团写 20~40 条就一定抽不全。
3. **端点只许填给定 id**，产出后统一校验：全库实测 **端点非法 0 条**。
4. **没有编年史的团用 `events` 回退源**：`characters.json` 里的 `events[]` 本来就逐条带出处
   （「段3 …」「XX战：…」），信息量足够推关系，而且出处能直接写进 `event` 字段当依据。
   全库 13 团里只有 3 团有编年史，**另外 10 团全靠这条回退路径**（否则根本补不动）。

## 六、顺手修掉的一个真 bug：`产出\<团>_关系网.md` 永远更新不了

查「关系线为什么少」时发现：**md 版关系网一直是旧的**，而且每跑一次 `visualize`
就多一个 `.trpg\reports\<文件>_自动更新建议.md`（当时堆了 6 个）。

**根因**（`trpg_agent\visualize\__init__.py`）：

| 位置 | 行为 |
|---|---|
| `relations_md()` / `jack_dossier()` / `universe_overview()` | 把 `<!-- AUTO-GENERATED by trpg-agent -->` 写在**文件末尾** |
| `_write_doc()` | 判断「是不是自动生成物」只看**开头 200 字** |

→ 生成端和检查端口径不一致：**自己生成的文件，下一轮就被自己当成"人工维护"**，
从此只写建议文件、不再更新。**连「跑团宇宙总览」其实也一直没被自动维护**（交接文档以为它是）。

**修法**：三个生成器改成把标记写在**首行**（`_write_doc` 本来就是往首行补标记，口径统一到"首行"）。

**存量文件**：已存在的 11 个 `<团>_关系网.md` + `跑团宇宙总览.md` 没有首行标记，
用新工具 `tools\_adopt_auto_marker.py` 补上（**逐份备份**在 `.trpg\reports\_adopt_bak_<时间戳>\`）：

```powershell
.\.venv\Scripts\python.exe tools\_adopt_auto_marker.py [--apply]
```

⚠️ **`产出\杰克档案.md` 不补** —— 那是手写正本，按设计就该走"建议文件"分支
（现在全库只剩它一份建议文件，这是**正确**状态，不是残留）。

**效果**：11 个关系网 md 全部就地重出，mg6 的从「44 角色 / 21 关系」变成「**48 角色 / 91 关系**」；
6 个失效的建议文件已清掉；`跑团宇宙总览.md` 也终于能被自动维护了。

> 另注：`visualize --all` 会给 manifest 里有、但一个角色都没有的团也出 **0 节点空图**
> （本次生成了「卧槽是伪人群·未归类」「小雪里克与叮咚鸡的粪海求生物语」两张空图，已删）。
> `tools\check_html.py` 会把 0 节点图判为 FAIL，所以别 `--all` 完不检查。
> 另外 `visualize --all` **不会**重出各团的 `<团>_关系网.md`（那段代码在 `if group:` 里），
> 要逐团 `--group X` 跑一遍。
